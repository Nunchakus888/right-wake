## Public download and fresh installation

After publication, an independent Linux x86_64 probe downloaded `install.sh` and `SHA256SUMS` from the public release URLs. The downloaded installer then fetched the public Linux x86_64 archive and installed it into a new directory whose path included spaces. It did not use `--from-dir`, a source build, an existing binary, or a privileged destination.

Verified results:

- Installer and checksum-file SHA-256 values matched the GitHub release metadata.

- Installed binary reported `waking 0.1.0`; size: `9,953,112` bytes.

This proves the actual public download/install path in a clean directory on that Linux host. It is not a claim that a real user's Mac, desktop session, or Linear workspace has been configured.

## Container and Codex plugin

The container workflow built the actual Dockerfile, ran as non-root, executed the synthetic demo, and started the real receiver with no public network access. Restarting the container, then replacing it while retaining its named volume, preserved the original events, completed jobs, and unsent drafts. This does not establish replay of a pending real-provider backlog or public relay operation.

## Remaining deployment acceptance

The [full ledger](../acceptance.md) retains all 32 original scenarios and the user's existing-thread requirement. Before enabling a real integration, record its actual host/version and existing thread, prior-history continuity, concurrency and tool boundaries, authorized provider event and exact reply destination, and live HTTPS/WSS behavior. Actual launchd/systemd user service lifecycle also requires a target-machine check.

The current adapters are Codex App Server and a configured GenericCommand. Waking does not yet implement an OpenAI-managed Codex Cloud task adapter. See [deployment](../deployment.md) and [Linear setup](../linear.md) for supported setup paths and the distinction from an existing Linear MCP connection.
