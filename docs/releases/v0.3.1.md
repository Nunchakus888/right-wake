# RightWake 0.3.1: persistent relay connection

This source/release candidate improves long-lived ingress without adding a relay
service dependency, database service, message broker or runtime package manager.
Publication status and measured tests are recorded in
[0.3.1 verification](v0.3.1-verification.md). A version bump or installer pin is
not a published package.

## What was already present

The 0.3.0 relay verifies raw provider bytes and the initial timestamp window,
commits them to its existing SQLite store, and delivers normalized envelopes
over a source-scoped device WebSocket. Durable received/executed receipts and
event/job deduplication already survive process loss. Compose already provides
the cloud process restart policy and persistent named volume.

The gaps were in the local process lifecycle: the device URL lived only in
arguments, `relay connect` stopped after transport failure, and the native user
service always executed `serve`.

## Minimum implementation

| Area | Change |
| --- | --- |
| Saved connection | Optional `config.json.relay_connection` with a WSS URL, token environment-variable name and exact source IDs. `relay configure` is idempotent and starts nothing; `relay show` also exposes existing paired-device references. |
| Transport | Bounded reconnect backoff, matching Ping/Pong liveness, connection deadlines and sanitized errors. One local engine/profile lock survives link loss; network failure does not restart in-flight model work. |
| Supervision | One owned service can explicitly run `serve`, `relay connect` or `relay serve`. Existing mode/private environment references are preserved; a mode change requires stopping the old process. |
| Guidance | Fixed infrastructure, independent webhook, explicit provider receive scope, current/previous assignment recovery and original-host/tool isolation are separate stages. |
| Diagnostics | A saved connection, initialization handshake or declared flag is never reported as verified network receipt, owning Desktop attachment, effective tool isolation or execution. |

There is no database migration in this patch: schema 4 and locked dependencies
are unchanged. The original profile, source IDs, bindings, paired device,
credentials, drafts, queue and onboarding baseline remain in place.

## Existing installation sequence

Use the installed schema and the original profile/environment-file paths. The
following sequence applies only after the controlled relay/device exists and
the old owned service has been inspected. Placeholders are not deployment
resources or authorization.

```sh
right-wake --data-dir /absolute/existing/profile --json relay show
right-wake --data-dir /absolute/existing/profile --json service status
# Stop the existing owned receiver before changing its saved connection/mode.
right-wake --data-dir /absolute/existing/profile service stop
right-wake --data-dir /absolute/existing/profile relay configure \
  --url wss://relay.example.com/relay/existing-device \
  --token-env RIGHT_WAKE_RELAY_DEVICE_TOKEN --source existing-source
right-wake --data-dir /absolute/existing/profile \
  --env-file /absolute/existing/private.env service install --mode relay-connect
right-wake --data-dir /absolute/existing/profile service start
right-wake --data-dir /absolute/existing/profile --json service status
```

Skip the configure/change steps when the existing references and service mode
already match. Never stop unrelated services or overwrite another webhook.
The new worker preserves the current pause state. Before resuming, reconcile
the current assigned-to-me list **and each previously tracked issue**, using
explicit owners/revisions from authorized read tools; omitted issues in a
partial import do not become unassigned. Preserve `linear-onboarding.json`
verbatim and record new receipt/coverage/recovery evidence in a private sidecar.

## Deployment and execution boundaries

- Fixed ingress requires an authorized online server/container with durable
  storage, a controlled hostname/TLS route and its continuing operation. The
  source code does not supply those resources. Keep Codex control endpoints
  private; expose only the exact webhook and paired-device routes.
- A named account-backed tunnel can provide a stable hostname when properly
  configured. A tunnel terminating on an offline laptop cannot store webhooks;
  put the existing RightWake relay on the online side for offline receipt.
  Third-party TLS ingress sees the payload it terminates. A URL or HTTPS alone
  is not provider or device authorization.
- macOS LaunchAgents restart after GUI login; Linux user services need a user
  manager and separately authorized lingering for pre-login startup. Templates
  do not prove actual startup on a user's machine.
- The original Desktop App Server connection and effective automatic-turn
  tool restrictions remain unverified deployment prerequisites. Do not start a
  second App Server against the same thread history or set a declaration flag
  as a substitute. Writable Linear MCP access on that thread remains a blocker
  for an unproved drafts-only execution boundary.
- Relay v1 has no replay-complete watermark. A restored connection does not
  prove all ownership updates have arrived; filtering uses latest observed
  state. Reconcile initial/provider gaps and offline backlogs needing current
  owner assurance before processing. This patch does not promise a provider
  current-state transaction or global exactly-once execution.
