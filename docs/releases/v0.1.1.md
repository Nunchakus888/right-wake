# RightWake v0.1.1

This update refreshes the embedded database and adds a practical Docker distribution path for an online VPS relay. The recommended placement is a native local worker beside the original agent thread, with an optional Docker relay receiving events while that worker is offline.

The [experimental prerelease](https://github.com/Nunchakus888/right-wake/releases/tag/v0.1.1) was published on 2026-11-03 from commit [`f0ae3d8fc408ef14b8b53409381bd3ebf0856cda`](https://github.com/Nunchakus888/right-wake/commit/f0ae3d8fc408ef14b8b53409381bd3ebf0856cda). [The v0.1.1 verification record](v0.1.1-verification.md) records completed local checks, successful release jobs, and independent public-download verification.

## Embedded SQLite update

| Dependency | v0.1.0 | v0.1.1 |
| --- | --- | --- |
| `rusqlite` | 0.32.1 | 0.41.1 |
| `libsqlite3-sys` | 0.30.1 | 0.39.1 |
| Bundled SQLite | 3.46.0 | 3.54.1 |

SQLite documents a rare [WAL-reset race that can corrupt a database](https://www.sqlite.org/wal.html#the_wal_reset_bug) when concurrent connections write/checkpoint under particular timing conditions. The mainline fix is included in [SQLite 3.51.3](https://www.sqlite.org/releaselog/3_51_3.html) and later. RightWake now bundles [SQLite 3.54.1](https://www.sqlite.org/releaselog/3_54_1.html) and checks the actually linked runtime before opening state, refusing versions older than 3.51.3. This is a runtime check, independent of the host's `sqlite3` command.

`waking --json doctor` includes `data.sqlite.version` and `data.sqlite.version_number`, so operators can inspect the linked library. SQLite remains part of the native binary and container image; no database server or separate SQLite installation is required. Updating an operating-system SQLite package alone does not replace RightWake's bundled library.

The RightWake database schema remains **version 3**. No new schema migration is introduced by this release. Source builds require Rust **1.89** or later; the repository still pins Rust **1.99.1**. Native release users do not need Rust.

## Docker image packages and Compose

The Linux release jobs reuse their already-built native binaries to produce the two architecture-specific images. This avoids a second Rust compilation for image packaging. The installer verifies the release checksum and image metadata, then loads `waking:0.1.1` into the selected Docker daemon. It does not start a container or write configuration/secrets.

The supplied Compose service defaults to `relay serve`, runs as UID/GID `10001`, persists configuration and SQLite state in a project-scoped named volume at `/data`, and publishes port 7433 only on host loopback. Operators explicitly initialize the profile, configure source/device scope and `private.env`, and start the service behind their own TLS proxy. `pull_policy: never` uses the loaded image; this distribution does not require GHCR publication or login.

The successful Linux checks verified SQLite 3.54.1 and preserved the original jobs/drafts plus a pending signed synthetic event across restart and container replacement. ## Upgrade and operating boundaries

Stop the receiver/worker and take a complete state backup before replacing its binary or image. Preserve native `config.json` and the whole data directory, or the Docker project's existing named volume and operator-managed `private.env`. Retain the same Compose project identity across recreation. A binary/image replacement does not require creating a new database or reassigning existing bindings.

A Docker relay receives and retains admitted events. The native local worker continues the original local thread when available; the relay does not migrate that history, Codex login, or worktree into the cloud. Execution on the VPS instead needs a supported agent host and existing session on that server. There is no OpenAI-hosted Codex Cloud adapter in this release.

Real Codex model continuation, concurrent desktop writers, public HTTPS/WSS delivery, and provider read/write E2E keep their separate requirements in [acceptance](../acceptance.md). Replies remain drafts until independently approved, and unknown execution/publication outcomes require reconciliation.
