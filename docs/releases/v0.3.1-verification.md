## Reliability evidence

### Saved settings and service definitions

`relay_config_contract` runs the actual CLI in separate processes against a
profile missing the new field, as in 0.3.0. It verifies the stable saved WSS URL,
idempotent connection/device reuse, all-or-none explicit overrides, invalid
endpoint/scope rejection, active-worker change refusal, private configuration
permissions and unchanged source/host/bindings/pause/database/onboarding/secret
files. Secrets remain environment-variable references.

Service tests cover generated systemd and launchd arguments, legacy `serve`
definitions, preserving an installed mode, refusing to drop its private
environment reference, requiring a saved connection and a stopped worker for
a mode change, and retaining existing profile data. These are definition and
ownership checks; **actual systemd/launchd startup and machine reboot were not
executed**.

### Protocol and actual process recovery

Relay unit/contract tests cover bounded backoff, startup offline, reconnect,
matching heartbeat timeouts, source/device authorization and revocation,
sanitized permanent TLS/auth errors, bounded frames/ACKs, database reopen,
lost-ACK replay and one canonical event/job after duplicate delivery.

The added `relay_process_contract` launches actual native children on a fixed
loopback HTTP/WS address with execution paused. It proves:

1. Invalid signature returns **401** without storing an event; a valid synthetic
   Linear comment is committed while the local worker is absent.
2. A cloud-process interruption after HTTP success preserves the event for the
   first local worker connection.
3. Restarting both cloud and local processes with the same address/profiles
   retains state and backfills the next offline event.
4. Restarting the cloud process alone reconnects the **same local worker PID**.
5. Duplicate canonical receipt creates no second event or queued fixture job;
   the one explicitly seeded job remains undispatched and draft count stays
   zero. Both configuration files remain byte-for-byte identical.

This fixture uses the explicit `--allow-loopback` test mode. It is not public
TLS/DNS, a real Linear delivery, actual OS supervision or a Desktop turn.

### Reuse of a 0.3.0 cloud relay

The same process fixture also passed with the retained public **0.3.0** Linux
x86_64 binary as the cloud receiver and this **0.3.1** build as the local worker.
The old binary's SHA-256 is
`0a2e37897359286cdbdb8db8d43e98b047f2cefc6972812e63dbba2160ae25a1`,
matching the earlier public-installation report. This run reused the previously
downloaded binary; it was not a fresh release download.

Reproduce with an explicitly selected trusted binary:

```sh
RIGHT_WAKE_TEST_RELAY_BIN=/absolute/path/to/right-wake-0.3.0 \
  cargo test --locked --test relay_process_contract -- --include-ignored
```

This supports keeping an already configured 0.3.0 cloud relay and upgrading
only the local worker. The version-crossing run is one repeat of the same test,
not another unique passing test in the total above.

### Personal assignment recovery

The existing personal-scope tests remain, with an additional onboarding-gap
scenario: the current assigned-to-me list omits a formerly owned issue, and the
old positive membership deliberately remains until that previous ID is
explicitly refreshed with its new owner. Importing current and prior ownership
facts suppresses the stale event while preserving the global execution pause
and all stored data. No model/provider call is made.

Relay v1 has **no replay-complete watermark**. Latest observed assignment state
is not an atomic provider-current snapshot. Connection/ACK success cannot by
itself certify recovery; initial activation, known provider gaps and backlogs
requiring current-owner assurance still need the documented read/import step.
